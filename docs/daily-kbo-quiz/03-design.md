# 2단계 설계 — "어제의 KBO 퀴즈"

- 상태: **제안(승인 전, 구현 없음).** 새 컬렉션을 더하는 DB 변경이므로 승인 뒤 진행한다. 기존 컬렉션은 바꾸지 않는다.
- 지키는 것: Spark 무료, Functions 없음, 회원·등수·점수·레벨 그대로, 권리 없는 기록 자동 수집 없음.

## 1. 흐름

```
[출처 어댑터]  → 검증 → 문항 생성 → 관리자 승인 → 공개 시각(06:00) → 비회원 화면 → 밤 집계
 테스트 데이터    순수 함수  틀 기반    source·정답 확인   규칙이 시각으로 공개
 (계약 후 교체)
```

어댑터만 출처에 의존한다. 나머지는 입력이 테스트 데이터든 계약 데이터든 똑같이 돈다.

**핵심 단순화 — 공개에 스케줄러가 필요 없다.** 승인할 때 `publishAt`(다음 06:00 KST)을 넣으면 보안 규칙이 `request.time >= publishAt`일 때부터 읽기를 연다. PC가 꺼져 있어도 공개된다.

## 2. 데이터(새 컬렉션)

| 경로 | 내용 | 읽기 | 쓰기 |
|---|---|---|---|
| `kboGames/{gameId}` | 경기 구조 데이터, `status`(`provisional`·`final`), `source`, `checks`, `isTest` | 관리자 | 관리자 |
| `kboSets/{date}` | `kind`(`quiz`·`no-game`·`rainout`·`season-end`·`review`), `gamesDate`, `publishAt`, `questions[]`(지문·보기·난이도, **정답 없음**), `state`(`draft`·`approved`·`held`), `withdrawn[]`, `isTest` | 공개 시각 뒤 누구나. `draft`·`held`·`isTest`는 관리자만 | 관리자 |
| `kboSets/{date}/keys/{i}` | 정답·해설·출처·기준일 | 관리자, 또는 **그 문제에 답을 낸 본인** | 관리자 |
| `kboSets/{date}/attempts/{uid}` | `guest`, `viewedAt`, `answers`(문제별 답·서버 시각), `signupClickedAt` | 본인 | 본인(규칙으로 제한) |

문서 ID가 날짜와 uid이므로 다시 돌려도 겹치지 않는다.

## 3. 정답 보호 — 서버 없이 바로 결과 보여 주기

공식전이 쓰는 규칙(앞 문제까지 답해야 다음 문제가 열림)을 정답에 쓴다.

```
match /kboSets/{date}/keys/{i} {
  allow get: if isAdmin()
    || (signedIn()
        && get(attempts/uid).data.answers.size() > int(i));   // 이 문제에 이미 답함
}
```

- 답은 한 번 쓰면 못 고치고 순서대로만 쓴다(공식전 규칙과 같음). **답을 낸 뒤에야 정답을 읽으므로 먼저 볼 수 없고, 보고 나서 고칠 수도 없다.**
- 묶음 파일에 정답이 없다. 해시로 숨기는 방식은 보기가 4개뿐이라 금방 풀려 쓰지 않는다.
- **남는 한계:** 익명 계정을 새로 만들어 답을 낸 뒤 정답을 보고, 다른 계정으로 맞힐 수는 있다. 비회원 점수는 공식 반영이 없어 얻는 것이 없으므로 받아들인다.
- 같은 방식이 공식전 문제 공개에서 돌고 있으나, 정답에 쓰는 것은 새로 규칙 테스트로 확인한다.

## 4. 검증과 문항 생성

순수 함수로 만들어 관리자 화면과 운영 스크립트가 함께 쓴다. **하나라도 실패하면 그 경기는 문항에 쓰지 않는다.**

| 검증 | 내용 |
|---|---|
| 중복 | 경기 ID + 날짜 |
| 정규화 | 팀명·선수명 표기 통일 |
| 점수 | 이닝 점수 합 = 최종 점수 |
| 승패 | 승리팀과 승리·패전투수의 소속 일치. 무승부는 승패 투수 없음 |
| 종료 | `final`만 사용. `provisional`은 대기 |
| 날짜 | KST 경기일 = 세트의 `gamesDate`. 오래된 경기를 "어제"로 표시 금지 |
| 정정 | 공개 후 값이 바뀌면 영향받은 문항을 자동 철회하고 관리자에게 표시 |

**문항:** 틀(템플릿)이 구조 데이터에서 정답을 꺼낸다. AI를 쓰지 않는다.

- 유형: 승리 팀, 최종 점수, 홈런 타자, 승리투수, 최다 타점, 연장·끝내기·완봉, 팀별 결과. 어려움은 장면 기반.
- 오답 보기: 그날 실제 출전 선수나 팀. 점수는 실제 점수와 가까운 값. 정답이 하나인지 검사하고, 동률이면 그 문항은 만들지 않는다(최다 타점 동률 등).
- 난이도: 5문제는 **쉬움 2·보통 2·어려움 1**(50·35·15에 가장 가깝다). 비율은 한 주 단위로 맞춘다. 문제 수는 세트별로 관리자가 바꾼다.
- 경기가 적어 문항이 모자라면 적은 수로 낸다. 지어내지 않는다.

## 5. 화면과 상태

홈에 카드 하나, 새 경로 `/yesterday`. 홈은 세트 문서 1회만 읽고 하루 동안 기기에 기억한다(`DEVICE_STORAGE_KEYS`에 추가).

| 상태 | 표시 |
|---|---|
| 퀴즈 있음 | "11월 5일 경기 퀴즈 · 5문제" |
| 경기 없음 / 우천 취소 | "어제는 경기가 없었어요" / "어제 경기는 우천 취소됐어요" + 오늘의 1이닝으로 안내 |
| 시즌 종료 | "2026 시즌이 끝났어요" + 돌아보기 세트. "어제"라고 쓰지 않음 |
| 준비 전 | "오늘 퀴즈를 준비 중이에요" + 가장 최근 세트(날짜 표시) |

풀이: 날짜·진행 표시 → 4지선다 → 답 저장 뒤 정답·해설·출처 → 끝나면 결과와 "가입하고 기록 쌓기" / "친구와 대결". 비회원 하루 3판 제한과 별개로 세며, 점수는 공식 등수에 들어가지 않는다.

**가입 시 결과:** uid가 유지되어 "내가 푼 기록"은 그대로 보인다. **포인트나 등수로 바꾸지 않는다.** 보상이 없으니 중복 지급과 조작 문제도 없다. 다만 이미 있는 계정으로 로그인하면 uid가 바뀌어 따라가지 않는다(현재 앱과 같음).

## 6. 지표 — 외부 도구 없이

이벤트를 따로 쓰지 않고 시도 문서에서 밤에 센다. 사람당 문서 하나라서 중복이 없다. 개인정보는 집계에 넣지 않는다.

| 이벤트 | 어떻게 세나 |
|---|---|
| `guest_quiz_view` | `/yesterday` 진입 시 시도 문서 생성(`viewedAt`). **홈 카드 노출은 세지 않음** |
| `guest_quiz_start` | 첫 답이 있는 문서(시작 단추만 누르고 답하지 않은 경우는 빠짐) |
| `guest_quiz_answer` | `answers` 개수, 문제별 정답률 |
| `guest_quiz_complete` | 답 수 = 문제 수 |
| `guest_signup_click` | `signupClickedAt` |
| `guest_signup_complete` | 다음 밤에 그 uid가 익명이 아니게 되었는지 |
| 재방문 | 같은 uid의 다음 날 시도 |

결과는 `adminDaily`에 숫자만 저장하고, 시도 문서는 30일 뒤 지운다(탈퇴 시에도 삭제).

## 7. 관리자

관리자 사이트에 "어제의 퀴즈" 화면 하나. 모든 쓰기는 규칙의 `isAdmin()`으로 지킨다.

- 경기 목록과 검증 결과, 실패 사유, 실행 기록
- 문항별 지문·정답·출처 확인, 승인·보류, 공개 후 철회
- 문제 수 변경, 다시 생성(같은 문서를 덮어쓰며 공개된 세트는 막음)
- "수동 새로고침"은 계약 후 어댑터 단계에서 작업 큐(`adminTasks`)로 넣는다. **서버가 없어 PC가 돌 때 처리되며 즉시 실행이 아니다.**

## 8. 자동 수집 단계의 실행 위치(계약 후)

| | 운영자 PC 06:00 작업 | GitHub Actions |
|---|---|---|
| 비용 | 0원 | 공개 저장소 0원 |
| 안정성 | PC·절전 해제 타이머에 달림(아직 꺼짐) | PC 불필요. 예약이 몰리면 늦을 수 있음 |
| 비밀 | 이미 PC에 있는 자격 증명 | 서비스 계정 키를 저장소 비밀값에 넣어야 함 |
| 판단 | 처음에는 이것 | 계약이 되고 지연이 문제 되면 옮김 |

여러 번 돌아도 문서 ID가 같아 중복 공개되지 않는다. 실패하면 이전 세트를 유지하고 `adminLogs`에 남긴다. **1차에는 스케줄러가 필요 없다**(§1).

## 9. 무료 한도(추정)

한 사람이 5문제를 끝까지 풀 때: 읽기 약 12(세트 1, 정답 5, 규칙의 시도 조회 5, 시도 1), 쓰기 6~7.

| 하루 완주 | 읽기(한도 5만) | 쓰기(한도 2만) |
|---|---:|---:|
| 100명 | 1,200 | 700 |
| 1,000명 | 12,000(24%) | 7,000(35%) |

기존 사용량과 합산되므로, 완주가 하루 1,000명에 가까워지면 다시 본다. 예상 운영비는 0원이다(계약 비용은 미확인).

## 10. 처리방침과 일정

비회원 시도 기록은 새 처리 내용이므로 **개정 공지 7일 뒤** 시작한다. 공지가 배포와 함께 나가므로 시작일은 배포일 + 7일이다.

| 순서 | 일 |
|---|---|
| 1 | 규칙·검증·생성·테스트(테스트 데이터만) |
| 2 | 비회원 화면·관리자 화면·지표 |
| 3 | 2026 시즌 돌아보기 세트(한국시리즈가 끝난 뒤 사람이 확인) |
| 4 | 승인 후 배포, 개정 공지, 7일 뒤 시작 |
| 5 | 계약이 되면 어댑터·예약 실행 |

## 11. 테스트 계획

테스트 데이터는 `isTest: true`이며 규칙이 일반 이용자에게 막는다. 에뮬레이터에서만 쓴다.

| 요구 | 방법 |
|---|---|
| 정상 종료, 경기 없음, 우천 취소, 연장·무승부, 포스트시즌 | 검증·생성 단위 테스트, 화면 E2E |
| 기록 정정, 수집 실패, 중복 실행 | 운영 스크립트 테스트(`tests/ops`) |
| 비회원의 정답 조회 시도(답 전, 남의 시도, 답 변경) | 규칙 테스트(`tests/rules`) |
| 비회원 → 회원 | E2E(uid 유지, 포인트 변화 없음) |
| 모바일·PWA | E2E 모바일 화면, 기존 PWA 확인 |
| AI 실패 | 해당 없음(AI를 쓰지 않음) |
