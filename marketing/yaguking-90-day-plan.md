## 1. 실행 요약

> **2026-11-01 기준선 반영:** 가입자 2·일 방문자 2·재방문율 100%(표본 2명)·담당 1명·예산 0원. 목표 수치는 [`05-baseline-reset-first-100-fans.md`](05-baseline-reset-first-100-fans.md) §3의 절대 목표를 따른다.

야구왕은 KBO 팬이 퀴즈를 한 이닝 경기로 즐기고, 타석 결과·박스스코어·응원 구단의 시즌 활동으로 다시 돌아오게 하는 무료 웹앱이다. 90일의 핵심은 크게 광고하는 것이 아니라, 야구 시즌이 없는 기간에도 반복할 이유를 만들고 그것이 실제 재방문으로 이어지는지 검증하는 것이다.

**세 가지 우선 베팅**

1. **친구 대결을 측정 가능한 초대 루프로 만들기:** 현재 구현된 6자 코드·초대 링크를 먼저 검증하고, 개인 경기 결과 공유 카드는 별도 제품 과제로 다룬다.
2. **매일/매주 돌아올 이유를 콘텐츠로 채우기:** 오늘의 야구 문항·공식전·월간 등수 등 이미 구현된 운영 기능을 안정적으로 공급하고, 짧은 설명형 콘텐츠와 연결한다.
3. **측정 가능한 소규모 공개:** 유입→첫 경기→완료→재방문을 익명/개인정보 최소화 원칙 아래 측정하고, 소규모 야구팬 커뮤니티에서 메시지와 리텐션을 검증한다.

현재 문서상 앱은 `https://yaguking.web.app`에서 운영 중이다. 따라서 90일 시작을 미래의 공개일로 가정하지 않고, 운영 중인 제품의 단계적 성장으로 계획한다. 계정·매출·예산·고객 지표는 미확인이다. 초기 2주간 기준선을 확보한 뒤 목표를 조정한다. 이 계획은 구단/선수 공식 로고·사진이나 미확보 기록 데이터 사용을 전제로 하지 않는다.

## 2. 제품 마케팅 컨텍스트

### 제품 개요

- **한 줄 설명:** KBO 상식과 기록 퀴즈를 투구·타격·아웃으로 풀고, 한 판의 박스스코어를 남기는 무료 야구팬 웹게임.
- **제품 범주/형태:** 한국어 소비자용 야구 퀴즈·팬 참여 웹앱/PWA. 무료 이용, Firebase Spark 기반으로 운영한다고 문서화되어 있으며 유료 상품은 확인되지 않았다.
- **핵심 행동:** 첫 경기 시작 → 3아웃까지 플레이 → 결과 확인 → 가입/다음 경기/친구 대결 → 11월 5일 이후 데일리 활동 → 주간·월간 재방문. 개인 경기 결과 공유는 아직 이 흐름에 없다.
- **주요 기능(구현 근거):** 개인 경기, 비회원 플레이, 문항 카테고리/난이도, 오답노트, 레벨 테스트·비공식 레벨, 친구 대결방과 초대 링크, 구단 프로필, 뉴스/공지, PWA 설치 유도, 운영자 대시보드. 출석·오늘의 공식전·월간 개인/구단 등수는 구현됐지만 2026-11-05 전에는 비활성이다. 루트 Next.js판의 선수 카드/개인 결과 공유 카드는 현 Firebase 운영판의 기능으로 간주하지 않는다.
- **제품 서사:** “퀴즈를 경기로 바꾼다.” 문제는 투구, 정답은 안타, 오답은 아웃, 3아웃이면 이닝 종료. 점수 한 번으로 끝나지 않고 내 타율/기록과 응원 구단 활동으로 이어지는 구조다.

### 우선 타깃과 사용 상황

1. **핵심:** KBO 경기를 꾸준히 보거나 특정 구단을 응원하며, 경기 사이에도 야구 콘텐츠를 소비하는 모바일 팬.
2. **인접:** 야구 규칙·기록을 배우고 싶은 초중급 팬, 친구와 가벼운 야구 퀴즈 대결을 원하는 그룹.
3. **공유를 만드는 사람:** 팬 커뮤니티 운영자, 야구 관련 소셜 계정/크리에이터, 야구를 소재로 대화를 여는 팬.

가설 JTBD: “경기 없는 날에도 야구 감각을 유지하고 싶다”, “내가 얼마나 아는지 짧게 겨뤄 보고 싶다”, “응원팀에 참여했다는 흔적을 남기고 싶다.” 이는 제품 기능에서 도출한 가설이며 인터뷰로 확인된 고객 발언이 아니다.

### 문제, 대안, 차별점

- **사용자 문제(가설):** 일반 퀴즈는 점수/정답만 남고 야구팬다운 성취감·응원팀 맥락·친구와 나눌 결과가 부족하다. 비시즌에는 반복 방문 계기가 약하다.
- **대안:** KBO 기록실/뉴스, 야구 커뮤니티와 SNS 퀴즈, 일반 퀴즈 앱, 친구끼리 직접 내는 문제. 이 대안들은 각자 정보 정확성·대화·범용성은 강하지만 게임 문법과 개인 기록의 지속성을 한 흐름에 묶지는 않는다.
- **차별화 가설:** 야구 경기처럼 진행되는 빠른 퀴즈, 타석 단위의 기록, 팬 참여/구단 활동, 링크 기반 친구 대결, 비회원 즉시 체험. 개인 경기의 공유 가능한 결과 카드는 제품 후보이지 현재 차별점이 아니다.
- **증거 한계:** 리뷰·사용자 인터뷰·활성/유지율·추천율 자료는 확인되지 않았다. “팬들이 사랑한다”, “가장 정확하다” 같은 검증되지 않은 주장은 사용하지 않는다.

### 포지셔닝 초안과 언어

**포지셔닝:** “야구를 아는 만큼 한 이닝으로 증명하는 KBO 팬 퀴즈.”  
**메시지 순서:** ① 한 이닝만 플레이 ② 정답은 안타, 오답은 아웃 ③ 내 박스스코어 확인 ④ 링크로 친구 대결 ⑤ 11월 5일 이후 출석·구단 대항전 참여.

**브랜드 톤(제품에서 추출):** 경기 중계처럼 명료함, 팬덤에 친근함, 결과와 규칙에 정직함. 과도한 승리 보장·공식 제휴 암시·팬덤 조롱은 피한다. 권장 표현은 “한 이닝 도전”, “오늘의 야구”, “내 박스스코어”, “응원팀에 한 점 보태기(비공식 참여)”이며 “KBO 공식”, “공식 기록 인증”, “실시간 공식 순위”는 권리/운영 근거 없이 사용하지 않는다.

## 3. 현황 진단

### 프로젝트 구조와 성장 표면

저장소에는 두 구현 축이 있다. 루트는 Next.js 16.4.2 + Supabase의 서버판이며 `README.md`에 미공개라고 적힌 과거 운영 기준이다. `firebase-app/`은 Vite/React/Firebase Spark판이며 최신 `firebase-app/docs/deploy.md`와 `deploy-log.md`는 실제 운영 중인 주소와 2026-10-29까지의 배포를 기록한다. 이 계획은 **현재 운영되는 Firebase 앱**을 우선 성장 표면으로 삼고, 루트 Next 앱을 별도 공개 대상으로 홍보하지 않는다.

## 4. 전략과 가설

### 시장 품질 게이트

핵심 문제는 **작음~중간 크기 × 중간 빈도**로 잠정 평가한다. 퀴즈는 긴급한 필수 과업이 아니지만, KBO 시즌·경기 화제와 맞으면 자주 소비될 수 있다. 비시즌 빈도와 반복 사용 가치는 아직 데이터가 없다. 따라서 현재는 낮은 비용의 팬 채널, 검색 가능한 상시 자산, 제품 내 공유에 집중하고, 유료 획득은 반복 사용이 증명된 뒤 판단한다.

### 90일 가설

- 친구 대결 초대는 일반 제품 소개 링크보다 신규 사용자의 대결 참가·완료율을 높일 것이다. **측정:** 초대 링크 복사, 초대 랜딩, 방 참가, 대결 완료. 개인 결과 공유는 구현 뒤 별도 가설로 검증한다.
- 오늘의 야구/주간 팬 활동 콘텐츠는 첫 플레이 이후 7일 재방문을 늘릴 것이다. **측정:** 코호트 D7과 7일 내 두 번째 완료 경기 비율.
- “팬 퀴즈”와 “한 이닝 경기” 중 경기 문법을 전면에 둔 메시지가 첫 경기 시작률을 높일 것이다. **측정:** 동일 커뮤니티/유입원별 랜딩 문구 비교.

### 계획 원칙

누적 자산을 만드는 편집 캘린더, 팬 커뮤니티에서의 유용한 참여, 제품 기능을 이용한 공유, 주간 지표 리뷰 순으로 작게 반복한다. 매주 짧은 원천 콘텐츠 하나를 만들고, 이를 블로그/뉴스·이미지 카드·짧은 SNS 문구로 재사용한다. 단발성 이벤트는 제품 데이터로 재방문을 확인할 수 있을 때만 연다.

## 5. AARRR 채널 계획

### Acquisition — 발견

**우선:** 검색/사이트 기본 정비, 야구 상식 콘텐츠, 커뮤니티 기여, 친구 대결 초대.

- 첫 2주: 운영 앱에서 `X-Robots-Tag: noindex`가 실제 확인된 상태이므로 검색 노출 허용 여부를 책임자가 결정한다. 허용 시 개인정보/약관·권리·색인 가능한 공개 페이지를 확인한 뒤 `noindex` 제거, canonical/title/description, OG 카드, 모바일 링크를 점검·배포한다. 결정 전에는 SEO 유입을 예측하지 않는다.
- 주 1회: 문항 하나에서 “오늘의 야구 상식” 설명 콘텐츠를 제작한다. 질문, 정답 근거/출처, 짧은 설명, 관련 플레이 링크를 포함한다. 선수 기록은 출처와 기준일을 명시하고 사용권을 확인한다.
- 주 2~3회: 야구 팬이 있는 공개 커뮤니티에 운영자 규칙을 지키며 참여한다. 순수 홍보글보다 퀴즈/설명 자료를 먼저 제공하고 링크는 허용될 때만 붙인다.
- 공유 루프: 현재는 친구 대결 대기실의 초대 링크 복사만 구현되어 있다. 링크 복사→초대 방문→방 참가→대결 완료를 식별하는 최소 집계를 우선 정의한다. 개인 경기 결과 공유 CTA/카드는 지표가 아니라 개발 후보로 백로그에 둔다.
- **보류:** 유료 검색/메타 광고, 인플루언서 비용, 대형 협찬. CAC·반복률·권리 범위·예산이 미확인이다.

### Activation — 첫 가치 경험

- 첫 방문 사용자가 로그인 없이 한 이닝을 시작할 수 있게 한다. 홈 첫 화면에서 플레이 시작과 경기 방식 설명을 짧게 보여준다.
- 1회차 종료 뒤 현재는 재도전·오답노트만 제공된다. 다음 행동 후보(가입/친구 대결/결과 공유)는 별도 UX 변경 과제로 검토하며, 이 문서 단계에서는 구현하지 않는다.
- 가입 전에 묻는 항목을 최소화하고, 가입/선호팀 선택의 각 이탈 지점을 계측한다.
- 초기 이벤트 이름은 `page_view`, `game_start`, `game_complete`, `signup_start`, GA4 권장 `sign_up`, `onboarding_complete`, GA4 권장 `share`, `room_join`, `room_complete`로 통일한다. `return_7d`는 이벤트가 아니라 닫힌 코호트에서 계산하는 지표다. 세션 ID·방 코드·정답·이메일 등 민감하거나 불필요한 값은 분석 이벤트에 넣지 않는다.

### Retention — 재방문

- “오늘의 야구” 또는 오늘의 경기 활동을 하루 한 번의 반복 포맷으로 고정한다. 매일 만들 수 있는 운영 용량과 문항 안전성부터 확인한다.
- 주간 팬 페넌트레이스 요약을 주 1회 발행: 참여자 수·구단 활동·내 기록을 설명하되 과장된 공식성 표현은 피한다.
- 뉴스/공지 영역은 제품 업데이트와 야구 상식 콘텐츠를 분리한다.
- 웹 푸시/이메일 발송은 동의 수집, 구현 상태, 개인정보 처리 근거가 확인되기 전까지 실행하지 않는다. PWA 설치 안내는 자발적 설치 맥락에서만 사용한다.
- 휴면 사용자를 직접 재접촉하는 캠페인은 연락처 수집·동의·발송 체계 확인 뒤 재검토한다.

### Referral — 팬 간 초대

- 먼저 초대 링크가 친구 대결에 바로 연결되는지, 링크 미리보기와 초대 출처 귀속을 추가할 수 있는지 확인한다. 현재 코드는 원본 `/room/{code}` 복사만 확인되며 귀속 파라미터는 확인되지 않았다.
- 친구 대결에는 “이번 주 우리 구단 대표 기록”처럼 공유할 이유를 붙인다. 리워드나 순위 조작 유인이 생기는 현금성 추천 프로그램은 만들지 않는다.
- 커뮤니티 운영자/야구 크리에이터에게는 유료 협찬보다 검증 가능한 퀴즈 묶음, 맞춤 친구 대결방, 미리 작성한 초대 문구를 제안한다. 명시적 동의와 표기 규칙을 따른다.
- 핵심 지표: 공유 클릭→초대 방문→게임 시작→완료 전환, 초대 1건당 완료 신규 사용자, 스팸/신고 비율.

### Revenue — 수익

현재 문서에서 유료 상품·매출·LTV를 확인할 수 없으므로 90일간 광고 수익 최적화나 구독 상품 출시를 목표로 하지 않는다. 앱 운영비와 무료 플랜 한도를 주간 확인하고, 광고 슬롯을 실제 노출하는 경우 사용자 경험·정책·권리·계약 상태를 점검한다. 유료 상품은 리텐션, 사용 의향 인터뷰, 비용 구조가 확인된 뒤 별도 검증한다.

## 8. 목표와 측정

### 북극성과 퍼널

**북극성:** 주간 유효 경기 완료 고유 사용자 수. Firebase판과 루트 PRD에서 “주간 유효 게임 완료 회원”을 북극성 후보로 삼았으나, 운영 앱의 공식 점수/회원 정의는 다를 수 있어 1주차에 확정한다.

| 지표 | 정의 | 90일 목표 설정 |
|---|---|---|
| 도달 | 채널별 랜딩/세션, 검색 노출 | 기준선 수집 후 증가율 목표 결정 |
| 활성화 | 신규 방문 중 첫 게임을 완료한 비율 | 첫 2주 기준선 후 상대 개선 목표 합의 |
| 가입 | 게임 완료 이후 가입 완료 비율 | 시작/완료 이벤트 정의 후 개선 |
| 리텐션 | 첫 완료 코호트의 D1/D7/D30 재방문 또는 재완료 | 관찰 기간이 끝난 코호트만 분모로 사용 |
| 추천 | 공유 클릭 중 초대 방문/완료 전환 | 공유 경로 QA 후 계측 가능 비율 산정 |
| 품질 | 신고·문항 정정·오류·무료 사용량 한도 | 권리/정확도 문제 0건 목표, 사용량 주간 감시 |

기존 PRD에는 90일 방문 30,000명·플레이어 10,000명·D7 25%·초대 유입 40%가 **검증되지 않은 가설 목표**로 남아 있다. 이를 확정 약속이나 예측으로 쓰지 않는다. 2주 기준선 후 현실성과 채널 용량에 맞춰 수치 목표를 정한다.

### 운영 대시보드

주간 한 페이지에 날짜/배포 버전, 채널별 방문, 게임 시작/완료, 신규/재방문, 가입, 공유/초대, 문항 신고·수정, Firebase 읽기/쓰기/전송량, 실험 결과를 기록한다. 분석은 동일 코호트와 닫힌 관찰기간을 쓴다. 샘플이 작으면 비율만 보고 결론내리지 말고 원시 수와 관찰 기간을 함께 적는다.

- **2분기:** 반복 플레이와 D7이 재현되고 운영 용량이 확인되면 팬 커뮤니티 협업, 격주 콘텐츠 시리즈, 이메일/푸시 동의 기반 리마인더를 검토.
- **3분기:** KBO 시즌 관심 피크를 고려해 승인된 데이터/브랜드 범위 내 팬 참여 캠페인과 크리에이터 협업을 파일럿. 이때도 예산은 단위경제가 설명될 때만 투입.
- **4분기:** 유료화 여부, 제휴 또는 후원 상품, 자동화 도구/전담 인력 필요를 실제 사용·비용 데이터로 결정.

새로운 채널 투자 전에는 D7/반복 플레이, 초대 유입 완료율, 콘텐츠별 완성 비용, 사용자 신고/정정률, 운영자의 주당 가용 시간을 검토한다. 다음 성장 단계와 펀딩 상태는 미확인이다.

## 12. 담당과 의사결정

저장소만으로 개인별 책임자를 식별할 수 없어 역할 기준으로 제안한다. 실제 이름을 시작 주에 채운다.

| 역할 | 책임 |
|---|---|
| 제품 책임자/창업자 | 최종 우선순위, 권리·약관·예산 승인, 메시지 검토 |
| 제품 운영자 | 문항 검수/출처, 뉴스/공지, 배포 상태, 사용자 문의 |
| 분석 담당(겸임 가능) | 이벤트 정의, 기준선, 주간 퍼널/코호트 보고 |
| 콘텐츠 담당(겸임 가능) | 주간 상식 카드/게시물, 커뮤니티 응답 |
| 법률/개인정보 검토자(필요 시 외부) | 데이터 사용권·처리방침·캠페인 동의 검토 |

한 사람이 여러 역할을 맡아도 된다. 단, 데이터/권리/개인정보와 관련한 공개 캠페인은 게시 전에 운영 책임자가 근거를 확인한다.
