## 1. 네 가지 성장 장치 한눈에

| 장치 | 구현 상태 | 지금 할 수 있는 것 | 제품 변경이 필요한 것 | 주로 만드는 것 |
|---|---|---|---|---|
| 퀴즈 결과 공유 | **미구현** | 운영자가 직접 캡처한 결과 화면을 콘텐츠로 사용, 사용자에게 자발적 캡처 요청 | 결과·업적 공유 카드와 공유 버튼 | 신규 유입 |
| 친구 대결 초대 | 구현(링크 복사) | 운영자가 대결방을 열어 단톡방·커뮤니티에 링크 배포 | 초대 출처 표시, 대결 뒤 "재대결·가입" 안내 | 신규 유입 → 가입 |
| 구단별 랭킹 | 구현, 11/5부터, 출석 팬 3명 이상만 공개 | "우리 구단 팬 3명 모으기" 캠페인, 주간 순위 카드 | 없음 | 재방문 + 같은 구단 팬 초대 |
| 일일 퀴즈(오늘의 공식전) | 구현, 11/5부터. **문항 45개(약 9일분)** | 문항 풀 운영 방식 결정 후 "어제의 정답 해설" 콘텐츠 | 없음(운영 문항 작성 필요) | 재방문 |

**성장 루프의 핵심 순서:**
`친구 대결로 처음 온다 → 비회원 3판을 쓴다 → 가입하며 최애 구단을 고른다 → 출석해 구단 순위에 기여한다 → 같은 구단 팬을 부른다 → 공식전으로 매번 돌아온다`

이 루프에서 **결과 공유만 빠져 있다.** 나머지 셋은 운영만으로 돌릴 수 있다.

## 2. 친구 대결 초대 (1순위: 신규 유입)

### 왜 1순위인가

가입자 2명 상태에서 낯선 사람에게 제품만 소개하면 반응이 약하다. 친구 대결은 **아는 사람이 보낸 링크**라서 클릭할 이유가 있고, 비회원도 이름만 적고 참가할 수 있다. [코드: 비회원 참가]

### 실행

| 단계 | 할 일 | 빈도 |
|---|---|---|
| 씨앗 | 운영자가 방을 만들어 지인 단톡방 3곳에 링크 전송(05 문서 씨앗 명단 20명) | 11/5~11/11 3판 |
| 정례화 | "금요일 밤 야구 퀴즈 대결" 고정 운영. Threads·Facebook 그룹에 방 링크 게시 | 매주 금 |
| 라이벌 대결방 | 1차 공략 구단 2개를 라이벌 짝으로 묶어 "잠실 더비방", "낙동강 더비방" 등 개설(조롱 없는 문구) | 격주 |
| 전환 | 대결이 끝난 뒤 운영자가 단톡방에 "기록 남기려면 가입하고 최애 구단 골라 주세요. 우리 구단 순위가 열려요" 한 줄 | 매 판 |

**초대 문구 예시**
- 단톡방: `야구 퀴즈 대결 열었어요. 설치 없이 이름만 쓰고 들어오면 돼요. 10문제, 5분이면 끝나요. 방 코드 {코드}`
- Threads: `금요일 밤 야구 퀴즈 대결방 열었습니다. 4명 차면 시작해요. 인필드 플라이 자신 있는 분 👉 {링크}`

### 제약

- 4명 방 한 판이 읽기 약 230회를 쓴다. 지금 규모에서는 문제없지만, 공개 대결방을 하루 수백 판 열 정도가 되면 무료 한도에 닿는다. [코드: usage-report]
- 정원은 기본 4명이다. 사람이 더 많으면 방을 여러 개로 나눈다.

## 3. 구단별 랭킹 (2순위: 재방문 + 같은 팬 초대)

### 현재 화면의 조건

구단 대항전은 **최애 구단(1위)이 같은 팬들의 이번 달 출석 일수 합**으로 순위를 매긴다. 출석 팬이 3명 미만인 구단은 순위에 나오지 않고, "같은 팬을 불러 모아 보세요!"라는 문구가 보인다. [코드: `RankingPage.tsx`]

이 조건이 오히려 초대 동기가 된다. 개인은 혼자 출석해도 구단 순위를 열 수 없으니, 같은 팬을 데려와야 한다.

### 캠페인: "우리 구단 첫 3명"

| 단계 | 내용 |
|---|---|
| 1 | 1차 공략 구단 2개(06 문서 §4.2)의 팬 커뮤니티에 "우리 구단 순위를 열 팬 3명을 찾습니다" 글. 규칙 퀴즈 3문항을 먼저 보여 주고 링크는 허용될 때만 |
| 2 | 3명이 채워진 구단이 생기면 "○○ 순위 열림" 축하 게시 → 다음 구단 모집 |
| 3 | 두 구단 이상 열리면 매주 월요일 순위 카드 발행(출석 일수 합, 참여 인원 대비 언급) |
| 4 | 월말 3일 전 "역전 가능" 리마인드(앱 공지 + SNS). 다계정·과도한 독촉 금지 |
| 5 | 매월 1일 지난달 결과와 칭호 발표, 새 시즌 개막 안내 |

### 재방문 효과를 키우는 장치(운영으로 가능)

- **출석 주간(포인트 2배):** 관리자 설정 `doubleDays`로 코드 배포 없이 켤 수 있다. [코드: engagement-plan §6] 순위 경쟁이 붙은 달의 마지막 주에 쓴다.
- **칭호:** 월간 등수에 따라 한 달 동안 닉네임 옆에 칭호가 붙는다. 발표 글에서 칭호 이름을 소개해 다음 달 동기를 만든다.

## 4. 일일 퀴즈 = 오늘의 공식전 (3순위: 재방문)

### 현재 상태

하루 한 번 5문제, 문항당 15초(서버 기한은 1초 여유). 정답은 기기에 없고 다음 날 새벽 운영자 PC 작업이 채점해 월간 등수에 넣는다. 어제 결과와 정답·해설은 다음 날 화면에서 보인다. [코드: `OfficialPage.tsx`]

**문제:** 문항 풀이 45개라 약 9일 뒤(11/13 무렵) "준비 중"이 된다. [코드: `ops/logs/cleanup.log` `remaining: 45`] 공식전 문항은 앱 문제은행과 겹치면 안 되므로 새로 써야 한다.

### 권장 운영: 주 3회 공식전 + 해설 콘텐츠 재사용

| 항목 | 권장 |
|---|---|
| 운영 요일 | 월·수·금(주 15문항). 11/5 시작 뒤 첫 9일은 기존 45문항으로 매일 운영하고, 그동안 주 3회 전환 여부 결정 |
| 문항 작성 | 주 15문항 ≈ 주 2시간. 05 문서의 주 5시간 중 블로그 1시간을 여기로 돌리고, 블로그는 해설을 재사용 |
| 홍보 문구 | "매일" 대신 "월·수·금 공식전". 운영 방식 결정 전에는 요일을 약속하지 않음 |

### 한 문항, 여러 번 쓰기 (content-strategy)

공식전 문항 1개는 채점이 끝난 다음 날부터 공개해도 된다. 이렇게 재사용한다.

| 시점 | 채널 | 형식 |
|---|---|---|
| 공식전 당일 | — | 앱 안에서만(정답 비공개) |
| 다음 날 | X·Threads | "어제의 공식전 가장 많이 틀린 문제" + 해설 (정답률 수치는 참가자가 30명 넘기 전까지 공개하지 않음) |
| 그 주 수요일 | 네이버 블로그 | 이번 주 공식전 해설 모음 "이번 주 규칙 정리" |
| 그 주 토요일 | Facebook 그룹 | 가장 토론거리가 될 만한 문항 1개로 투표형 게시 |

문항을 콘텐츠로 쓸 때도 출처·기준일 표기를 유지한다.

## 5. 퀴즈 결과 공유 (4순위: 제품 변경 필요)

### 현재 상태

개인 경기 결과(박스스코어)·업적 카드·레벨 테스트 결과를 앱 밖으로 내보내는 기능이 **없다.** 친구 대결 링크 복사가 유일한 공유 기능이다. [코드] 따라서 "결과를 공유해 보세요" 같은 문구를 홍보에 쓰지 않는다.

### 지금 할 수 있는 대체 방법

- 운영자가 직접 플레이한 결과·업적 화면을 캡처해 SNS 콘텐츠로 사용("사이클링 히트 이렇게 나옵니다").
- 커뮤니티 글에서 "레벨 테스트 몇 등급 나오셨어요?"처럼 **사용자가 자발적으로 캡처해 댓글로 다는** 흐름을 만든다. 강요하거나 보상을 걸지 않는다.

### 제품 요청 (04 문서 §7-① 구체화)

| 항목 | 요청 내용 |
|---|---|
| 공유 시점 | 개인 경기 결과 화면, 업적 획득 순간, 레벨 테스트 결과 화면 |
| 카드 내용 | 박스스코어 요약(안타·홈런·득점), 업적 이름, 닉네임(선택), 최애 구단 이름(글자), 서비스 주소 |
| 넣지 않을 것 | 로고·선수 사진, 정답 목록, 개인정보, "공식" 표현 |
| 동작 | 모바일은 `navigator.share`로 이미지+링크, 데스크톱은 이미지 저장 |
| 링크 | 공유 출처를 알 수 있는 파라미터(분석 도입 시 집계) |
| 확인 조건 | 처리방침·이미지 권리·링크 미리보기(OG) 점검 후 출시 |

출시 후 측정: 결과 화면 도달 대비 공유 비율, 공유 링크로 들어온 사람의 첫 경기 완료 비율.

## 6. 신규 가입 전환 (onboarding)

바이럴로 들어온 사람이 가입까지 가는 지점은 두 곳이다.

| 순간 | 현재 | 운영으로 할 일 | 제품 요청 |
|---|---|---|---|
| 비회원 3판 소진 | 하루 3판 제한 [코드] | 커뮤니티 글에 "가입하면 기록이 이어지고 구단 순위에 들어가요" 안내 | 소진 화면의 가입 안내 점검(04 문서 §7-②) |
| 친구 대결 종료 | 최종 순위 표시 | 운영자가 단톡방에 가입 안내 한 줄 | 대결 뒤 "기록 남기기(가입)·재대결" 버튼 |

가입 단계(연령 확인 → 닉네임 → 최애 구단)는 짧다. 가입을 설득할 때는 **최애 구단 선택 = 구단 순위에 참여**라는 연결을 앞세운다.

## 7. 측정

분석 도구가 없으므로 관리자 화면 숫자를 주 1회 손으로 기록한다(05 문서 §6). 장치별로 보는 숫자:

| 장치 | 주간 기록 | 판단 |
|---|---|---|
| 친구 대결 | 완료 판 수, 운영자 개설 방 vs 사용자 개설 방 | 사용자가 직접 연 방이 생기면 루프가 돌기 시작한 것 |
| 구단 랭킹 | 3명 이상 구단 수, 구단별 출석 팬 수 | 2주 안에 3명이 안 차면 그 구단 공략 방식 변경 |
| 공식전 | 참가자 수(관리자 이벤트 화면), 남은 문항 일수(`daysLeft`) | `daysLeft`가 7일 아래면 문항 작성 우선 |
| 결과 공유 | (미구현) 자발적 캡처 댓글 수 | 제품 요청 우선순위 근거 |

Firebase Analytics 도입 시 이벤트 이름은 [`02-kpi-firebase-analytics-plan.md`](02-kpi-firebase-analytics-plan.md) §5를 쓴다. 이 문서의 네 장치는 `share`(content_type `room_invite` / 향후 `result_card`), `room_join`, `room_complete`, `attendance_complete`, `daily_quiz_start`, `daily_quiz_submit`에 대응한다.
