# 공식 XP·RP 분리 설계 (7단계 — 설계만, 2026-10-26)

> **이 문서는 설계다. 앱 코드·워크플로·배포 규칙(`firestore.rules`)은 바꾸지 않았다.** 만들기 전에 §10의 결정이 필요하다.
> 설계의 핵심 가정 두 가지는 **시험용 규칙**(`docs/prototypes/official.rules`, 배포 안 함)으로 에뮬레이터에서
> 확인했다 — `tests/rules/official-prototype.test.ts`(§4.4).
> 제약: Spark 무료 플랜만, Cloud Functions·Blaze 없음, 기기가 조작할 수 있는 점수는 공식 랭킹에 넣지 않음,
> 실제 KBO 기록 자동 수집 없음, 실제 배포는 승인 후.

## 0. 요약

- 지금(1~6단계)의 점수·XP·등급은 **모두 비공식**이다. 정답(정적 JSON)과 시계가 기기에 있어 바꿀 수 있다.
  이 값은 앞으로도 공식 기록과 **섞지 않는다** — 화면에서 "연습 XP"로 따로 보인다
- 공식 기록은 **서버가 판정**해야 한다. 서버 코드를 못 돌리므로, **GitHub Actions 예약 작업**이 관리자 권한
  (Firebase Admin SDK)으로 판정한다. 기기는 답만 내고, 시각은 Firestore 서버 시각(`request.time`)이 찍는다
- 공식전 형태(권장): **하루 한 번 "오늘의 공식전" 10문제**. 앱 묶음에 없는 **별도 문항**을 쓰고, 정답은 판정
  일꾼만 읽는 곳에 둔다. 문제는 **하나씩만** 열린다(앞 문제에 답해야 다음 문제를 읽을 수 있음 — 규칙이 막음)
- 판정은 **매시 1번**(결과가 늦게는 1~2시간 뒤에 반영). 공식 XP·레벨·시즌 점수·리더보드를 일꾼만 쓴다
- **RP(Elo)는 PRD대로 2차.** 설계 초안(§6)만 둔다. 친구 대결은 계속 비공식(RP·XP 없음)

## 1. 왜 지금은 공식이 될 수 없나

| 조작 | 지금 막히나 | 공식에서 막는 법 |
|---|---|---|
| 정답 미리 보기 | ✗ — 정답이 앱 묶음(`questions.generated.json`)에 있다 | 공식 문항은 앱에 없다. 정답은 일꾼만 읽는 문서 |
| 문제 미리 모아 보기 | ✗ — 문제은행 전체가 기기에 있다 | 문제를 하나씩만 연다(규칙). 앞 문제에 답한 **서버 시각**부터 시간이 간다 |
| 응답 시간 줄이기 | ✗ — 기기 시계 | 답마다 서버 시각(`request.time`)만 받는다. 기기가 보낸 시간은 쓰지 않는다 |
| 점수·XP 직접 쓰기 | 비공식 문서에만 쓸 수 있다 | 공식 문서는 **기기 쓰기 금지**(규칙). 일꾼만 쓴다 |
| 다시 풀기 | 비공식은 마음대로 | 문서 ID = 사람 ID → 하루 한 번(만들기만 허용) |

## 2. 원칙 (01 PRD §7, 03 §5 승계)

1. 모든 공식 정답·점수·시간은 서버(일꾼) 판정. 정답은 공식전이 닫히기 전에는 기기에 주지 않는다
2. 답은 문항마다 처음 한 번만 인정(규칙이 덮어쓰기를 막음)
3. XP는 **원장(지급 내역) + 멱등 키** `eventType:entityId:userId` — 일꾼이 두 번 돌아도 두 번 주지 않는다
4. 비공식 값(연습 XP, 친구 대결 점수, 비공식 레벨 테스트 등급)은 공식 계산에 **입력으로도 쓰지 않는다**
5. 무료: Spark 그대로(결제 계정 없음), GitHub Actions 무료 분량 안, 쓰기를 판당 한 자릿수로

## 3. 구조

```
[운영자 PC / 비공개 저장소]          [GitHub Actions — 예약]                  [Firestore]
 공식 문항 풀(정답 포함, 비공개) ─▶ publish(하루 1번, 전날 23시) ──────▶ officialRounds/{날짜}           (문제, 정답 없음)
                                                                    officialKeys/{날짜}             (정답 — 기기 읽기 금지)
                                    grade(매시 :07) ◀── 읽기 ──────── officialRounds/{날짜}/attempts/{uid}  (기기가 답을 하나씩 추가)
                                            └────── 쓰기 ──────────▶ officialResults/{날짜_uid}     (판정·XP 지급 내역 = 원장)
                                                                    officialStats/{uid}             (공식 XP·레벨·시즌 점수)
                                                                    leaderboards/{시즌}/entries/{uid} (공개 닉네임·점수)
```

- **일꾼 권한**: 서비스 계정 하나, 역할은 `Cloud Datastore User`만. 키 파일 대신 **Workload Identity Federation**
  (GitHub OIDC → 짧은 토큰). 키 파일을 써야 하면 GitHub Secrets에 두고 90일마다 교체
- Admin SDK는 보안 규칙을 건너뛴다 → 일꾼 코드가 곧 서버 규칙이다. 리뷰·테스트 대상
- Spark에서도 Admin SDK로 Firestore를 쓸 수 있다(사용량은 같은 무료 한도에서 빠진다)

## 4. 데이터와 규칙(초안)

### 4.1 공식전 문제 — `officialRounds/{roundId}` (roundId = KST 날짜 `20261027`)

| 필드 | 뜻 |
|---|---|
| `opensAt`, `closesAt` | KST 00:00 ~ 23:59 |
| `total` | 문항 수(10) |
| `version`, `poolVersion` | 문항 풀 판, 정정 추적 |
| `answersRevealed` | 닫힌 뒤 일꾼이 정답·해설을 붙인다(복습용) |

문항은 하위 문서 `questions/{0..9}` — `stem`, `options`, `category`, `difficulty`, `basisDate`, `opensAt`.
**정답 없음.** 규칙(요지 — 전체는 `docs/prototypes/official.rules`):

```
match /officialRounds/{roundId}/questions/{index} {
  // 공식전이 열려 있고, 내 시도에서 index번 앞까지 답했을 때만 읽는다(다음 문제 미리 보기 금지)
  allow get: if isMember() && request.time >= resource.data.opensAt
    && get(/databases/$(database)/documents/officialRounds/$(roundId)/attempts/$(request.auth.uid))
         .data.answers.size() >= int(index);
  allow list, write: if false;
}
match /officialKeys/{roundId} { allow read, write: if false; }   // 일꾼(Admin SDK)만
```

### 4.2 시도 — `officialRounds/{roundId}/attempts/{uid}` (기기가 쓰는 유일한 공식 문서)

| 필드 | 규칙 |
|---|---|
| `startedAt` | 만들 때 `== request.time` |
| `total` | 공식전 문서의 `total`과 같아야 한다(줄여서 빨리 끝내기 금지) |
| `answers` | **맵** `{"0": {choice, at}, "1": …}`. 한 번에 키 하나만 추가, 키 = 지금 크기, `at == request.time`, `choice ∈ A~D 또는 null`(시간 초과) |
| `graded` | 만들 때 `false`. 기기는 못 바꾼다 |

- 기한: 규칙이 `request.time <= startedAt + duration.value(total × 16 + 1, 's')`로 계산한다. 기한 필드를 두지
  않는 이유 — 기기는 "서버 시각 + N초"라는 값을 보낼 수 없다(시험 중에 찾은 문제)

- 배열이 아니라 맵인 이유: 서버 시각(`serverTimestamp`)은 배열 안에 넣을 수 없다
- 문서 ID = 사람 ID → **하루 한 번**. 만들기는 만 14세 확인 회원만(비회원은 공식전 없음 — PRD)
- 응답 시간 = `answers[i].at − answers[i−1].at`(첫 문제는 `startedAt`부터). 공식전에는 문항 사이 정답 화면이 없다
  (다 끝난 뒤에 보여 준다). 네트워크 지연을 감안해 15초 + **1.5초 여유**를 넘으면 시간 초과로 판정

### 4.3 일꾼만 쓰는 문서 (기기 쓰기 금지)

| 문서 | 내용 | 읽기 |
|---|---|---|
| `officialResults/{roundId}_{uid}` | 문항별 정답 여부·시간·점수, **XP 지급 줄**(`[{key, event, xp}]`) | 본인 |
| `officialStats/{uid}` | 공식 XP, 레벨, 시즌 점수, 공식전 수, 연속 참여, 오늘 지급 횟수(일 한도 계산용) | 본인 |
| `leaderboards/{season}/entries/{uid}` | 닉네임, 시즌 점수, 공식전 수 | 로그인한 누구나 |
| `leaderboards/{season}` | 상위 100명(문서 하나 — 화면은 1읽기) | 로그인한 누구나 |

- **원장 = 결과 문서.** 일꾼은 결과 문서를 `create()`로 만든다 — 이미 있으면 실패하므로 같은 시도에 XP를 두 번
  주지 않는다(멱등). 결과 문서 + 공식 통계 + 리더보드 항목을 **한 트랜잭션**으로 쓴다(시도당 쓰기 3 + 시도 표시 1)
- 정정·취소는 지우지 않고 반대 줄(`xp: −n`)을 단 정정 문서로(03 §5)
- 내 순위: `entries`에서 내 점수보다 높은 수를 세는 집계 쿼리(`count()`, 1,000개당 1읽기)

### 4.4 에뮬레이터로 확인한 것 (시험용 규칙)

| 가정 | 결과 |
|---|---|
| 서버 시각을 **맵 안**에 받아 `at == request.time`으로 검사 | ✅ 된다. 기기 시각(10초 전)은 거절 |
| 앞 문제에 답해야 다음 문제를 읽음(하나씩 열기) | ✅ 된다. 시작 전 0번, 0번 답 전 1번 읽기 거절 |
| 건너뛰기·고쳐 쓰기·두 개 한꺼번에·지우기·`graded` 바꾸기 | ✅ 모두 거절 |
| 시작 시각 지어내기·문항 수 줄이기·하루 두 번·비회원 | ✅ 모두 거절 |
| 기한(문항당 16초 + 1초) 뒤의 답 | ✅ 거절 |
| 정답 문서 읽기, 공식 통계 쓰기 | ✅ 거절. **배포 규칙에서도** 공식 경로는 지금 모두 막혀 있음 |

검사 두 줄(`at == request.time`, 하나씩 열기)을 빼면 해당 테스트가 실패하는 것도 확인했다.

## 5. XP·레벨 (01 PRD §6, 03 §4~5 승계 — Firebase판에서 줄 수 있는 것만)

| 이벤트 | XP | Firebase판 | 이유 |
|---|---:|---|---|
| `answer_correct` | +10 | ✅ 공식전 | 일꾼이 판정 |
| `hard_correct_bonus` | +5 | ✅ 공식전 | 〃 |
| `daily_complete` | +30 (일 1회) | ✅ 공식전 완료 | 〃 |
| `streak_7d` | +100 (7일 주기 1회) | ✅ 공식전 7일 연속 | 일꾼이 날짜로 계산 |
| `placement_grant` | 배정 레벨 최소 XP (1회) | ⏸ 보류(§10-4) | 지금 레벨 테스트는 기기 채점 |
| `solo_complete` | +20 | ❌ | 개인 퀴즈는 기기 채점 |
| `friendly_complete` / `friendly_win` | +20 / +30 | ❌ | 친구 대결은 기기 채점 |
| `review_five_complete` | +20 | ❌ | 복습은 기기 채점 |

- 레벨 임계값 `[0, 500, 1500, 3500, 7000, 12000, 20000]`, 표기는 야구 등급(육성선수 … 명예의 전당)
- MVP 자동 승급은 **Lv3까지**(PRD). Lv4~7은 2차 승급 시험
- 하루 최대 공식 XP ≈ 10×10 + 5×(어려움 수) + 30 ≈ 150 → Lv3(1,500)까지 약 10일
- 공식전 점수(시즌 점수): 정답 100 + floor(50 × (15 − t) / 15), 연속 정답 보너스 3연속 +30, 5연속마다 +70(PRD §6)

화면: 마이 탭에 **공식 레벨·XP**(일꾼이 쓴 값)와 **연습 기록**(비공식)을 다른 카드로. 리더보드는 공식만.

## 6. RP(Elo) — 2차, 초안

PRD: 공식 1:1 랭크전만, 초기 1000, K=32(첫 20전)/16, 승 1·무 0.5·패 0. 친선(친구 대결)은 미지급.

실시간 1:1은 서버 없이 공정하게 맞추기 어렵다 → **비동기 랭크전** 초안:

1. 랭크전 대기열 문서에 들어간다(`rankedQueue/{uid}` — 기기는 자기 것만 만들기·지우기)
2. 일꾼(매시)이 RP가 가까운 두 사람을 묶어 대전과 문제(4.1과 같은 하나씩 열기)를 만든다
3. 두 사람이 24시간 안에 각자 푼다(4.2와 같은 시도 문서)
4. 일꾼이 둘 다 끝났거나 기한이 지나면 판정: 점수 → 맞힌 시간 합 순, 같으면 무승부. 안 푼 쪽은 패
5. Elo 갱신을 한 트랜잭션으로(대전 문서 `create`가 멱등 관문)

## 7. 일정과 무료 분량

| 작업 | 언제 | 하는 일 | GitHub 분(추정) |
|---|---|---|---|
| `publish` | 매일 KST 23:00(다음 날 공식전) | 풀에서 10문항 골라 문제·정답 문서 생성, 전날 공식전에 정답 공개 | 월 30분 |
| `grade` | 매시 :07 | 끝났거나 기한 지난 시도 판정, 통계·리더보드 반영 | 월 약 720분 |
| `cleanup`(8단계) | 매일 | 끝난 대결 방·오래된 비회원 기록 지우기 | 월 30분 |

- GitHub 무료: **공개 저장소는 표준 실행기 무료**, **비공개는 월 2,000분**. 위 합계 약 800분 → 비공개여도 안
- 예약 실행은 **5분보다 짧게 못 하고**, 몰리면 수십 분 늦거나 빠질 수 있다 → 일꾼은 "아직 안 한 것 전부"를
  처리하게(놓쳐도 다음 실행이 따라잡음). publish는 하루 일찍 만들어 두고 `opensAt`으로 연다
- 저장소에 60일 활동이 없으면 예약 작업이 꺼질 수 있다 → 운영 점검표에 넣는다
- GitHub 결제 수단·예산은 $0 → 넘치면 멈추고 청구되지 않는다. Firebase는 결제 계정을 연결하지 않는다

### Firestore 사용량(공식전 1판, 10문제)

| 누가 | 읽기 | 쓰기 |
|---|---|---|
| 기기 | 공식전 1 + 문제 10 + 규칙 get 10~11 + 결과 1 ≈ **23** | 시도 1 + 답 10 = **11** |
| 일꾼 | 시도 1 + 정답(공식전당 1) + 통계 1 ≈ **3** | 결과 1 + 통계 1 + 리더보드 1 + 시도 표시 1 = **4** |
| 리더보드 보기 | 상위 100 문서 1 + 내 순위 count 1 | 0 |

- 공식전까지 하는 회원 하루 ≈ 쓰기 18(6단계 표) + 15 = **33** → 20,000 ÷ 33 ≈ **600명/일**(공식전 없이 1,100명)
- 쓰기를 더 줄일 후보: 답을 2개씩 묶어 보내기는 시간 측정이 흐려져 하지 않는다. 대신 일꾼의 "시도 표시"를
  결과 문서 존재로 대신하면 판당 1 줄어든다(시도 조회를 결과 없는 것만 고르는 쿼리로 바꿀 수 있을 때)

## 8. 남는 위험

| 위험 | 정도 | 대응 |
|---|---|---|
| 친구끼리 오늘 문제·정답을 공유 | 중 | 모두 같은 문제를 푸는 하루 공식전의 한계. 이상 점수(전부 1초대 정답)는 일꾼이 표시 → 운영자 확인. 문항 풀을 크게, 보기 순서를 사람마다 섞는 안(일꾼이 사람별 문제 문서를 미리 만들면 쓰기 증가)은 2차 |
| 검색해서 15초 안에 답 | 중 | 모든 퀴즈 공통. 시간 점수가 빠를수록 커서 이득이 작다 |
| 여러 계정 | 중 | 공식전은 확인 회원만. App Check(무료 월 1만 건) 도입은 배포 때 결정 |
| 일꾼 키 유출 | 높음 | WIF(키 없음), 최소 역할, 워크플로 파일 보호(브랜치 보호·리뷰) |
| 정답이 저장소에 올라감 | 높음 | **공식 문항 풀은 저장소에 두지 않는다**(공개 저장소면 특히). 운영자 PC → 일꾼이 Secrets 또는 비공개 저장소에서 읽음 |
| 예약 실행 지연·누락 | 낮음 | 따라잡기 처리, 화면에 "결과는 보통 1~2시간 안에" |
| 문항 정답 오류 | 중 | 정정은 반대 지급 줄로. 문항마다 근거·기준일(기존 원칙) |

## 9. 만들 때 순서(승인 후)

1. 공식 문항 풀 준비(운영자 작성·검수, 기존 문제은행과 겹치지 않게, 자동 수집 없음)
2. 보안 규칙 + 규칙 테스트: 시도 만들기·답 하나씩·서버 시각·기한, 문제 하나씩 읽기, 공식 문서 기기 쓰기 금지
3. 일꾼(`ops/official/`: `publish.mjs`, `grade.mjs`) + 에뮬레이터 테스트(Admin SDK를 에뮬레이터에 붙여
   판정·멱등·일 한도·연속 참여·정정)
4. 워크플로 파일은 **`workflow_dispatch`(수동)만** 켜 두고 시작 → 확인 후 예약(`schedule`) 추가
5. 화면: 오늘의 공식전, "판정 대기" 화면, 공식 레벨 카드, 리더보드
6. GCP 쪽 설정(WIF 풀·서비스 계정) — 실제 Firebase 프로젝트가 있어야 하고 사용자가 한다(8단계 배포 준비와 함께)

워크플로 초안(만들지 않음):

```yaml
name: official-grade
on:
  workflow_dispatch:            # 처음에는 수동만
  # schedule: [{ cron: '7 * * * *' }]   # 승인 후
permissions: { contents: read, id-token: write }
concurrency: { group: official-grade, cancel-in-progress: false }   # 겹쳐 돌지 않게
jobs:
  grade:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@<고정 SHA>
      - uses: google-github-actions/auth@<고정 SHA>
        with: { workload_identity_provider: ${{ vars.WIF_PROVIDER }}, service_account: ${{ vars.GRADER_SA }} }
      - run: npm ci && node ops/official/grade.mjs
```
