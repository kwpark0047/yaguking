# 야구왕 — "최신정보" 일일 자동 갱신 기획

> **Firebase 무료판 안내(2026-10-26)** — 이 문서의 플랫폼 부분(Supabase·Vercel·서버 판정 등)은 16 문서(무료 플랜 Firebase 전환) §4의 "12" 줄로 바뀌었다. 본문은 그대로 둔다.

- 작성일: 2026-10-26 · 상태: **기획안 (구현 승인 문서 아님)**
- 요청: koreabaseball.com에서 매일 최신 데이터를 크롤링해 메인 페이지 최신정보란에 올린다
- 관계: 01 PRD §데이터 원칙, 05 문서 §주의사항, 06 문서 D4 "그날의 야구", 10 문서 구간 C, 11 문서 §2

## 0. 한 줄 결론

**koreabaseball.com을 승인 없이 크롤링하는 방식은 채택하지 않는다.** 사이트의
robots.txt와 이용약관이 자동 수집을 명시적으로 금지하고, 이 프로젝트의 문서도
같은 원칙을 이미 정해 두었다. 대신 약관이 스스로 열어 둔 **두 출구 — 운영사의
사전 서면 동의, 또는 KBO 공식 API** — 를 통해 같은 목표(매일 자동으로 갱신되는
최신정보란)를 이룬다. 그 계약 하나가 최신정보란뿐 아니라 그동안 막혀 있던
**D4 "그날의 야구"와 구간 C 문항 700+**까지 함께 푼다.

계약 전에도 최신정보란은 **수집 없이** 열 수 있다(§4.2). 화면과 수집 파이프라인은
데이터 출처와 무관하게 설계해, 계약이 성사되는 날 어댑터 하나만 갈아 끼우면 된다.

## 1. 사실 확인 (2026-10-26 직접 열람)

### 1.1 robots.txt — `https://www.koreabaseball.com/robots.txt`

- 첫 줄 주석: 데이터를 **사전 승인 없이 자동 수집·크롤링·복제하는 행위를 금지**한다는 고지
- 주요 검색엔진(Googlebot, Yeti, Daumoa, Bingbot)만 허용하고 그마저 `/ws/`(데이터 경로로 보임)는 차단
- 그 밖의 모든 봇은 `User-agent: *` / `Disallow: /` — **사이트 전체 차단**

### 1.2 이용약관 — `https://www.koreabaseball.com/Etc/Policy.aspx` (2024-02-26 시행)

- 운영 주체: **스포츠투아이㈜** — KBO 공식 기록 데이터를 다루는 곳. 그대로 협상 상대가 된다
- **제14조 차목 (크롤링 등 자동화 수집 행위의 금지)**
  - 회사의 **사전 서면 동의** 또는 **KBO가 제공하는 공식 API** 없이 크롤러·스크래퍼·매크로·봇으로
    경기 결과·선수 통계·분석 데이터를 대량·반복 수집하는 것을 금지
  - 수집한 데이터를 재판매·재배포하거나 **타 플랫폼에 연동하거나 2차 가공**하는 것도 금지
  - 위반 시 요청 제한, 계정·IP 제한, 법적 조치를 단계적으로 취할 수 있다고 명시
- **제17조 나항**: 서비스에서 얻은 정보를 가공·판매하는 등 **상업적 사용 불가**. 단 회사나 제휴사의
  **사전 동의**가 있으면 가능
- 제21조 나항 13호: 사전 승낙 없이 복제·유통·상업적 이용 시 이용계약 해지 사유

> 요청한 기능("매일 크롤링 → 우리 메인에 표시")은 약관이 금지하는 **자동 수집**과
> **타 플랫폼 연동** 두 가지에 그대로 해당한다.

### 1.3 이 프로젝트가 이미 정해 둔 원칙

| 문서 | 내용 |
|---|---|
| 01 PRD | 상업적 데이터 사용권 범위를 법적 검토 전 확정하지 않는다. 무단 대량 수집 금지 |
| 05 실행계획 | 데이터 사용권 확인 전 비허가 데이터 스크래핑을 수행하지 않는다 |
| 06 V2 기획 | 불변 전제: 실제 KBO 기록 데이터 사용권 미확보 |
| 10 문항계획 | 구간 C(상세 기록·그날의 야구)는 기록 DB 사용권 필요 — 불가 |

### 1.4 하지 않은 것

공식 사이트의 비공개 데이터 경로(`/ws/` 등)나 내부 요청 구조는 **분석하지 않았다.**
그 분석 자체가 무단 수집 준비가 되기 때문이다. 이 문서의 기술 설계는 특정 사이트
구조에 의존하지 않는다.

## 2. 왜 "그냥 조심스럽게 긁는" 방식도 안 되는가

| 흔한 생각 | 실제 |
|---|---|
| 하루 한 번이면 "대량·반복"이 아니다 | 매일 자동 수집은 그 자체로 반복이다. 약관은 횟수가 아니라 **자동화 수단**을 문제 삼는다 |
| 점수·순위는 사실이라 저작권이 없다 | 개별 사실은 그렇다. 그러나 약관 위반, robots 위반, 데이터베이스 제작자 권리, 부정경쟁 관련 쟁점은 별개다. **법적 판단은 법무 검토 사항**이며 여기서 단정하지 않는다 |
| 요청 간격을 늘리고 UA를 바꾸면 된다 | 차단 회피는 위반을 **고의**로 만든다. 채택하지 않는다 |
| 문제 되면 그때 멈추면 된다 | 약관은 **IP 차단**을 명시한다. 그날 최신정보란은 빈 화면이 되고, 운영 중인 서비스 신뢰가 깎인다. 법적 조치 고지도 있다 |

실무 위험만 봐도 결론은 같다. **언제 끊길지 모르는 출처 위에 매일 노출되는 화면을
올리면 안 된다.**

## 3. 목표를 다시 정의한다

**"메인에 매일 자동으로 갱신되는, 믿을 수 있는 최신정보란"**

| 성공 기준 | 값 |
|---|---|
| 신선도 | 경기 종료 후 **2시간 이내** 반영 (권리 확보 후) |
| 표기 | 모든 정보에 **기준 시각과 출처** 표시 |
| 장애 시 | 빈 화면 없음 — 마지막 정상 데이터 + "○시 기준" |
| 권리 | 모든 항목이 출처·라이선스·권리 근거를 가진다(문항 `rights_note`와 같은 원칙) |
| 끄기 | 권리 문제가 생기면 코드 수정 없이 즉시 중단(`LATEST_FEED=off`) |

## 4. 데이터 경로 — 3단

### 4.1 경로 A: 공식 라이선스 / 공식 API — **권장**

약관 제14조·제17조가 직접 열어 둔 길이다.

- **문의 상대**: 스포츠투아이㈜(약관상 운영사) 및 KBO
- **하나의 계약이 푸는 것**

| 지금 막혀 있는 것 | 근거 문서 |
|---|---|
| 최신정보란 일일 자동 갱신 | 이 문서 |
| D4 "그날의 야구" — 날짜 기반 문항 자동 생성 | 06 문서 D4, 10 문서 §2.3(보류) |
| 구간 C 문항 700+ (시즌 성적·선수 기록) | 10 문서 §1.2 |
| `KBO 역사`·`선수 기록` 카테고리 확충 | 10 문서 §1.2.4 |

- **문의서에 반드시 넣을 질문** (답에 따라 설계가 바뀐다)
  1. 제공 범위: 경기 결과·일정·팀 순위·선수 시즌 기록·박스스코어 중 무엇까지
  2. 갱신 주기와 지연: 경기 종료 후 몇 분 안에 받을 수 있나
  3. 형식: API(인증 방식·호출 한도) / 파일 전송 / 웹훅
  4. **2차 가공 허용 여부** — 퀴즈 문항 생성은 2차 가공이다. 이게 안 되면 D4·구간 C는 여전히 막힌다
  5. 표시 조건: 출처 표기 문구, 로고 사용 가능 여부, 노출 위치 제한
  6. 저장·캐시: 보관 기간, 계약 종료 시 삭제 의무
  7. 상업 조건: 광고·유료 기능이 있는 서비스에서 써도 되는가, 비용 구조
  8. 시범 기간·소규모 노출(P1) 조건 — 11 문서의 노출 일정과 맞물린다
- **공식 API의 존재**: 약관이 "KBO가 제공하는 공식 API"를 언급하지만, 공개된 개발자 API는 확인하지 못했다. 있는지부터 묻는다

### 4.2 경로 B: 계약 전 — **수집 없이** 여는 최신정보란

계약을 기다리는 동안에도 화면은 연다. 외부 데이터를 긁지 않는 모듈만 쓴다.

| 모듈 | 데이터 | 권리 |
|---|---|---|
| **오늘의 야구** 참여 현황 | 우리 DB (오늘 참여 수, 평균 득점) | 자체 데이터 |
| **랭킹 변동** | 우리 DB (어제 대비 순위 변화) | 자체 데이터 |
| **이번 주 문항 소식** | 우리 DB (새 문항 수, 카테고리) | 자체 데이터 |
| **오늘 KBO 경기 보러 가기** | 공식 사이트 일정·결과 페이지로 **링크만** | 링크는 복제가 아니다. 프레임으로 감싸지 않고 새 창으로 연다 |
| **운영자 한 줄 소식** | 운영자가 검수 콘솔에서 직접 작성 | ⚠ 경기 결과 같은 사실을 사람이 옮겨 적는 것도 약관 제17조(상업적 사용) 쟁점이 남는다 — **법무 확인 후** 켠다. 그 전에는 자체 소식(이벤트·업데이트)만 쓴다 |

이것만으로도 "매일 바뀌는 메인"은 된다. 자체 데이터는 매일 실제로 변한다.

### 4.3 경로 C: 서면 동의를 받은 수집

공식 API는 없고 운영사가 **서면으로** "이 범위를 이 주기로 가져가도 된다"고 허락한
경우에만 쓴다. 이때 수집 어댑터는 동의서의 조건(대상 경로, 주기, 식별 가능한
User-Agent, 연락처)을 **코드 설정으로 고정**하고, 동의서 사본 위치를 `rights_note`에
남긴다. 동의 없이 이 경로를 켤 수 없도록 기본값은 꺼짐이다.

## 5. 화면 기획 — 최신정보란

### 5.1 어디에 두는가

"메인 페이지"가 사용자에 따라 다르다.

| 사용자 | 메인 | 최신정보란 위치 |
|---|---|---|
| 비회원 | `/` = **첫 타석** | **첫 타석 앞에 두지 않는다.** 08 문서 §3 "첫 투구까지 0탭" 원칙과 충돌한다. 대신 결과 화면 하단 · 모드 선택 상단 · lg 경기 화면 우측 정보 패널 |
| 회원 | `/dashboard` (홈 "덕아웃") | 히어로 카드 바로 아래 |

### 5.2 구성 (계약 후 기준, 계약 전에는 §4.2의 모듈로 채운다)

아래 점수·순위는 **배치를 보여 주기 위한 가짜 예시**다. 실제 데이터가 아니다.

```
┌ 최신정보 ─────────────────── 10/25 23:41 기준 · 출처 ┐
│ ● 내 구단  LG 5 : 3 KIA   승 · 3연승                 │  ← 구단 테마색(카드 범위)
│                                                       │
│ 어제 경기          오늘 경기                          │
│ 두산 2:7 삼성 ▸    18:30 SSG vs 롯데                  │
│ 한화 4:4 NC   ▸    18:30 키움 vs KT                   │
│ …더보기                                               │
│                                                       │
│ 팀 순위 1 LG  2 삼성  3 KIA  …            전체 ▸      │
│                                                       │
│ [ 어제 경기로 만든 오늘의 야구 하러 가기 ]  ← D4      │
└───────────────────────────────────────────────────────┘
```

- **내 구단 우선**: 대표 구단 경기를 맨 위에, 그 카드만 구단 테마색(08 문서 §2.5 `TeamScope`)
- **기준 시각과 출처를 항상** 카드 머리에 둔다(문항의 `record_as_of`·출처 표기와 같은 원칙)
- 우천 취소·서스펜디드·노게임은 점수 대신 상태 글자로(색만으로 표시하지 않는다)
- 비시즌(11~3월): 경기 모듈을 접고 "개막까지 D-○" + 자체 데이터 모듈

### 5.3 반응형

| | sm (360~599) | md (600~1023) | lg (1024+) |
|---|---|---|---|
| 대시보드 | 1열, 내 구단 + 어제 경기 3개 + 더보기 | 2열(어제/오늘) | 2열 + 순위 줄 |
| 결과 화면 | 접힌 카드(제목 + 내 구단 한 줄) | 펼침 | 펼침 |
| 경기 화면 | 표시 안 함(타석 집중) | 표시 안 함 | 우측 정보 패널 하단 |

### 5.4 접근성

- 경기 결과는 표 시맨틱(`<table>` + 캡션 "어제 경기 결과, 10월 25일")
- 점수는 "LG 5 대 KIA 3, LG 승"처럼 읽히게 `aria-label`
- 승패를 색만으로 표시하지 않는다 — 글자("승/패/무")와 함께
- 고대비 스타일(08 문서 §2.6)에서 표 경계 3:1

## 6. 시스템 설계 — 출처와 무관하게

### 6.1 흐름

```
스케줄러(플랫폼 무관)
   │  POST /api/internal/latest-feed/run  (비밀 토큰)
   ▼
수집 작업 ── 출처 어댑터 ── (A 라이선스 API | B 자체 DB | C 동의 수집)
   │
   ▼
검증 ──실패──▶ 격리 + 운영자 알림 (화면은 마지막 정상본 유지)
   │통과
   ▼
스냅샷 저장 (feed_snapshots: 원본 + 정규화본 + 출처·권리)
   │
   ├─ 사실 데이터(점수·순위·일정) ──▶ 자동 게시
   └─ 문항 초안(D4) ─────────────▶ draft → 검수 콘솔 승인 (기존 원칙)
   │
   ▼
읽기 모델 (feed_items) ──▶ 화면은 **우리 DB만** 읽는다 (외부를 직접 부르지 않는다)
```

화면이 외부 출처를 직접 호출하지 않는 것이 핵심이다. 출처가 느리거나 죽어도 메인은
마지막 정상본으로 뜬다.

### 6.2 어댑터 인터페이스

```ts
/** 최신정보 출처. 계약이 바뀌면 이것만 갈아 끼운다. */
interface LatestFeedSource {
  id: 'licensed-api' | 'internal' | 'consented-fetch';
  /** 이 출처를 써도 되는 근거. 없으면 작업이 시작되지 않는다. */
  rights: { licenseId: string | null; note: string; displayCredit: string };
  fetch(window: { from: Date; to: Date }): Promise<RawFeed>;
  normalize(raw: RawFeed): FeedItem[];
}
```

- `rights.licenseId`가 없는 외부 출처는 **켜지지 않는다**(코드로 막는다)
- 표시 문구(`displayCredit`)는 계약서의 출처 표기 조건을 그대로 넣는다

### 6.3 데이터 모델 (초안)

| 테이블 | 용도 |
|---|---|
| `feed_sources` | 출처, 라이선스 ID·기간, 표시 문구, 켜짐 여부 |
| `feed_runs` | 실행 기록(시작·끝·건수·오류) — 운영 콘솔에 표시 |
| `feed_snapshots` | 수집 원본과 정규화본, 보관 기간(계약 조건) 후 삭제 |
| `feed_items` | 화면이 읽는 항목: 종류(경기·순위·일정·소식), 기준 시각, 출처, `rights_note` |

RLS는 기존 원칙대로 읽기 정책만, 쓰기는 서버 작업만.

### 6.4 스케줄 (한국시간)

KBO 리그 규정 제21조의 경기 개시 시간(평일 저녁, 주말 오후)을 기준으로 잡는다.

| 시각 | 작업 | 이유 |
|---|---|---|
| 23:30 | 당일 결과·순위 | 저녁 경기 종료 후 |
| 06:00 | 재확인 | 우천 취소·서스펜디드·기록 정정 반영 |
| 12:00 | 당일 일정 | 선발 예고 반영 |
| 비시즌 | 하루 1회 | 일정 공지·시상만 |

스케줄러는 배포 환경이 정해지지 않았으므로(11 문서 §2.2) **특정 플랫폼에 묶지
않는다.** 내부 엔드포인트 하나를 두고 Vercel Cron, Supabase pg_cron, GitHub Actions
중 무엇이 불러도 되게 한다. 같은 시간대 재실행은 멱등이어야 한다(스냅샷 키 = 출처 + 기준 시각).

### 6.5 검증과 격리

- 형식 검증(스키마)
- 상식 검증: 10개 구단, 점수 0 이상, 순위표 경기 수의 합이 맞는가, 같은 경기가 두 번 없는가
- 전일 대비 이상치: 순위가 한 번에 5계단 이상 뒤집히면 보류
- 실패 시: 그 실행분만 격리, 화면은 마지막 정상본 + "○시 기준", **2회 연속 실패면 운영자 알림**

### 6.6 끄는 법

- `LATEST_FEED=off` — 최신정보란 전체를 자체 데이터 모듈로 되돌린다
- 출처별 `feed_sources.enabled` — 운영 콘솔에서 하나만 끈다
- 구단 테마(`TEAM_THEMES`)와 같은 원칙: 권리 문제가 생기면 **코드 수정 없이** 멈춘다

### 6.7 테스트

- 계약 테스트: 공급사 샘플 응답을 픽스처로 — **CI에서 외부를 호출하지 않는다**
- 시간대: 한국시간 자정 경계, 경기 종료가 자정을 넘는 경우, 서머타임 없음 확인
- 장애: 출처 타임아웃·빈 응답·형식 변경 시 화면이 마지막 정상본을 유지
- 권리: `licenseId` 없는 외부 출처가 켜지지 않는지

## 7. 고도화 — 데이터가 게임이 되는 지점

계약이 2차 가공을 허용하면(§4.1 질문 4) 최신정보는 **읽을거리에서 끝나지 않는다.**

1. **D4 "그날의 야구"**: 어제 경기 결과 → 문항 초안 자동 생성("어제 LG–KIA전 결승타는 몇 회?") → 검수 콘솔 승인 → 오늘의 야구 모드 출제. 최신정보란 하단 버튼이 바로 그 경기로 연결된다
2. **내 구단 개인화**: 내 구단 경기 문항을 우선 출제, 내 구단이 이긴 날은 결과 화면 연출 강화
3. **기준 시즌 자동 표기**: 데이터의 시즌을 문항 `season_scope`에 자동으로 채운다 — 2026 규정 문항에서 손으로 하던 일

## 9. 사람이 정해야 할 것
