# 야구왕 P1 소규모 노출 — 남은 일 점검표

> **Firebase 무료판 안내(2026-10-26)** — 이 문서의 플랫폼 부분(Supabase·Vercel·서버 판정 등)은 16 문서(무료 플랜 Firebase 전환) §4의 "11" 줄로 바뀌었다. 본문은 그대로 둔다.

작성일 2026-10-24 · 기준 커밋: `feat/p1-one-inning`

노출의 목적은 **"결과를 저장하려는 순간 가입으로 넘어가는 비율"**을 재는
것이다(06 문서 §7). 그 수치를 얻지 못하면 노출할 이유가 없으므로, 아래
점검표는 "서비스가 뜨는가"가 아니라 **"수치를 얻을 수 있는가"**를 기준으로
정렬했다.

기능은 완성됐고 로컬에서 검증됐다. **막는 것은 세 가지다 — 배포할 환경이

### 1.1 가장 큰 구멍이었던 것 — 정답 위치 쏠림

노출 직전에 발견했다. 정답이 **A에 53.5%, D에 0.8%** 몰려 있었다.
문항을 읽지 않고 A만 찍어도 절반을 맞히는 상태였고, 이 게임은 **정답 속도가
타구 결과를 정하기 때문에** 읽지 않고 찍는 쪽이 홈런을 치는 구조가 된다.
기믹 자체가 무력해진다.

원인은 작성자(나) 습관이다. CSV를 쓸 때 정답을 첫 보기에 두는 일이 잦았다.

- 적재 시 **본문 해시로 라벨을 섞도록** 바꿨다(`labelPermutation`).
  난수가 아니라 해시라서, CSV를 다시 적재해도 같은 배치가 나온다.
- 기존 505문항은 `npm run content:rebalance`로 재배치했다. 같은 함수를 쓰므로
  **DB 상태와 CSV 재적재 결과가 일치한다**(재검사 0건 변경으로 확인).
- 보기 행의 id는 건드리지 않았다. `at_bats.option_id`가 지난 경기 기록으로
  그 id를 들고 있다.
- 유니크 제약을 지연 가능하게 바꾸는 마이그레이션이 필요했다(0014).
  네 행의 라벨을 동시에 바꿔야 해서 즉시 검사로는 교환이 안 된다.
- 회귀 방지 테스트를 넣었다(`tests/unit/content/labelPermutation.test.ts`).

남은 찍기 경로: **가장 긴 보기 찍기가 31.2%**(무작위 25%). 6%p 이득이고
보기를 다 읽어야 해서 시간이 든다. 막으려면 오답을 정답과 비슷한 길이로
다시 써야 하는데, 기계가 판단할 일이 아니라 사람 검수로 넘긴다.

## 2. 노출을 막는 것 (사람이 정해야 함)

### 2.1 개인정보 처리방침 — **최우선**

법적 판단이라 내가 쓸 수 없다. 대신 **문안에 들어갈 사실 관계는 코드에서
확정했으니** 그대로 쓰면 된다.

> **자리 페이지 (2026-10-26)**: `/terms`(이용약관)와 `/privacy`(개인정보처리방침)가
> 생겼다. 문안은 비어 있고 "확정 전 · 시행일 미정"만 표시한다. 로그인·가입 화면의
> 동의 문장과 메인 페이지 바닥글이 이 두 페이지로 연결된다(동의 문장에도 "두 문서는
> 아직 확정 전입니다"를 밝혔다). 문안이 확정되면 `src/components/legal/LegalPlaceholder.tsx`
> 대신 본문과 시행일을 넣는다. **자리 페이지가 있다고 노출 차단이 풀린 것은 아니다.**
>
> **초안과 보관 기간 (2026-10-26)**: `/privacy`에 처리방침 초안을 실었고 보관 기간을 정해
> 자동 파기로 뒷받침했다. 만 14세 미만 가입은 서버에서 막는다. 남은 것은 빈칸(운영 주체,
> 보호책임자, 리전 등)과 법률 검토다 — **15 문서**.
>
> **시행 (2026-10-26)**: 운영자가 빈칸을 입력하고 법률 검토 항목을 확인해, 처리방침을 시행본으로
> 바꿨다(시행일 2026-10-26). 리전·안전 조치는 기본값이며 배포가 그와 맞아야 한다(OPERATIONS.md).
> **이용약관은 아직 자리 페이지다.**

| 수집 항목 | 어디에 | 법적 근거가 필요한 지점 |
|---|---|---|
| 이메일 | `auth.users` | 계정 식별·로그인 |
| 닉네임, 대표 구단 | `profiles` | 서비스 제공 |
| 경기 기록(타석·판정·점수) | `at_bats`, `play_sessions` | 서비스 제공 |
| 통산 성적, XP, 랭킹 | `user_batting_stats`, `xp_transactions`, `leaderboard_entries` | 서비스 제공 |
| 게스트 토큰 해시 | `guest_sessions.token_hash` | 비회원 체험 상한(하루 2이닝) |

- **보관 기간**: 정하지 않았다. 정해야 한다.
- **삭제 경로**: 구현돼 있다. 설정 화면 → 닉네임 입력 확인 → 계정과 기록 삭제.
  `auth.users`까지 지우고 세션·리프레시 토큰도 정리된다(검증 완료).
- **내 데이터 내보내기**: 구현돼 있다(설정 화면).
- **제3자 제공·국외 이전**: 현재 Supabase 한 곳. 호스팅 리전은 배포 환경을
  정할 때 확정된다 — 문안보다 §2.2가 먼저다.

### 2.2 배포 환경 — 대상이 없다

스테이징도 운영도 아직 없다. 정해야 할 것:

- 호스팅(앱) / Supabase 프로젝트 리전 — 개인정보 문안에 들어간다
- 도메인
- 운영 Supabase의 `site_url`과 `additional_redirect_urls`
  **로컬에서 이것 때문에 매직링크가 조용히 엉뚱한 곳으로 갔던 적이 있다.**
  Supabase는 등록되지 않은 redirect를 말없이 `site_url`로 떨어뜨린다.
  배포 직후 **반드시 실제 로그인 왕복을 한 번 해봐야 한다.**
- 필요한 환경변수: `DATABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
  `GUEST_TOKEN_SECRET`, **`TRUSTED_PROXY_COUNT`(배포 구성에 맞춰야 함, §3.1)**,
  (선택) `DATABASE_POOL_MAX`, `NEXT_PUBLIC_AUTH_PROVIDERS`
- 비워 둘 것: `RATE_LIMIT`(E2E 전용), `SEARCH_INDEXING`(공개 전까지)

### 2.3 퍼널 계측 — 한 단계를 못 잰다

`npm run funnel`이 이미 재는 것(새로 수집하는 것 없이 상태 테이블만 읽는다):

```
게스트 발급 → 체험 시작 → 경기 완료 → 가입 완료 → 게스트 기록 승계
```

**못 재는 것:**

- 결과 화면을 보고 **가입을 시작했으나 끝내지 않은 사람**
  (매직링크 요청이 어디에도 남지 않는다)
- 게이트를 닫고 계속 논 사람 / 그냥 떠난 사람의 구분
- 유입 경로

`growth_events` 테이블은 **있지만 기록하는 코드가 없다.** 0행이다.

이걸 붙이는 건 기술적으로 어렵지 않다. 다만 **새로운 수집을 시작하는
일이고 개인정보 처리방침에 적을 내용이 늘어난다.** 그래서 내 판단으로
붙이지 않았다. §2.1과 함께 정해야 한다.

> **결정이 필요한 질문**: 가입 이탈 지점을 재기 위해 익명 식별자 기반
> 이벤트를 적재할 것인가? 안 한다면 "가입 완료율"까지만 보고 중간 이탈은
> 추정으로 남는다.

### 3.1 레이트 리밋 (2026-10-24 완료)

비회원 체험 상한(하루 2이닝)은 **게스트 토큰** 단위라 쿠키를 버리고 새로
받으면 무한히 우회된다. 실제로 쿠키 없이 경기 시작을 연타하니 요청마다 새
게스트로 통과했다. 토큰과 무관한 축으로 주소 기준 리밋을 붙였다.

| 경로 | 한도 |
|---|---|
| 경기 시작 `POST /play/sessions` | 6회/분 |
| 타석 제출 `POST /play/sessions/:id/at-bats` | 120회/분 |
| 기록 승계 `POST /auth/claim-guest` | 10회/분 |

- 카운터는 Postgres에 둔다(마이그레이션 0015). 배포 대상이 정해지지 않았고
  인메모리 카운터는 서버리스나 다중 인스턴스에서 사실상 동작하지 않는다.
- **IP 원문을 저장하지 않는다.** `GUEST_TOKEN_SECRET`으로 HMAC한 값만 남긴다.
  처리방침이 확정되기 전에 새 식별자를 평문으로 쌓지 않기 위해서다.
- 카운터 조작이 실패하면 통과시킨다. 같은 DB를 쓰므로 그때는 요청도 어차피
  실패한다.

**구현 중 내 실수 하나를 잡았다.** 처음에는 `x-forwarded-for`의 **첫** 주소를
썼다. 리버스 프록시는 클라이언트가 보낸 헤더 뒤에 실제 주소를 덧붙이므로
첫 값은 클라이언트가 정한다. 첫 값만 바꿔 10번 보내자 **10번 모두
통과했다.** 오른쪽에서 신뢰 프록시 수만큼 들어간 자리를 쓰도록 고쳤고,
같은 시도가 6번 통과 후 막히는 것을 확인했다.

> **배포 시 반드시 맞출 것**: `TRUSTED_PROXY_COUNT`. 너무 작으면 CDN 주소를
> 사용자로 착각해 정상 사용자가 429를 받고, 너무 크면 위조가 다시 통한다.
> 프록시 하나면 1(기본), CDN 뒤 로드밸런서면 2. 배포 직후 §5의 확인을 한다.

E2E는 한 주소에서 여러 브라우저를 병렬로 돌리므로 `RATE_LIMIT=off`로 띄운
서버에서 돈다(Playwright 설정에 반영). **운영에서는 이 값을 비워 둔다.**

### 3.2 검색 노출 차단 (2026-10-24 완료)

- `robots.txt`: 기본 `Disallow: /`
- 레이아웃 메타: `noindex, nofollow`

robots.txt는 크롤링만 막을 뿐이라 외부 링크로 들어온 URL은 색인될 수 있다.
그래서 둘을 함께 쓴다. `SEARCH_INDEXING=allow`일 때만 열리며, 비워 두거나
오타가 나면 차단 쪽으로 틀린다.

## 5. 노출 당일 순서 (제안)

1. 운영 DB에 마이그레이션 적용 → `npm run db:fingerprint`로 대조
2. CSV 7개 적재 → `npm run content:check` **오류 0건 확인**
3. 매직링크 로그인 왕복 1회 (§2.2의 함정)
4. 계정 삭제 1회 — 처리방침에 적은 대로 실제로 지워지는지
5. **레이트 리밋 확인** (§3.1) — 실제 프록시를 거쳐 경기 시작을 7번 연타해
   7번째가 429인지, 그리고 `x-forwarded-for` 앞쪽 값을 바꿔 보내도
   여전히 막히는지 본다. 둘 중 하나라도 어긋나면 `TRUSTED_PROXY_COUNT`가
   틀린 것이다
6. `/robots.txt`가 `Disallow: /`인지, 페이지에 `noindex`가 있는지 확인
7. 노출 시작
8. 매일 `npm run funnel`로 단계별 수치 기록
9. 표본이 쌓이면 P2 우선순위 결정 (10 문서 §2.3)

## 6. 한 줄 요약

**§3의 레이트 리밋과 검색 차단은 끝냈다.** 오류 모니터링만 남았고, 그건
배포 환경에 따라 도구가 달라진다. 노출을 막고 있는 건 개인정보 처리방침(§2.1)과 배포 대상(§2.2)이며
둘 다 사람의 결정이다. 퍼널 이벤트(§2.3)는 그 결정에 딸려 온다.
