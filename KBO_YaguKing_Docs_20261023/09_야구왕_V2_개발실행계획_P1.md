### 3.1 핵심 결정 — 타석 쓰기는 왜 `postgres.js`인가

`supabase-js`에는 **다중 문장 트랜잭션이 없다.** 그런데 타석 제출 1회는 다음을 **원자적으로** 처리해야 한다(07 §5.3).

1. 세션 행 잠금(`select ... for update`) → 동시 제출 경합 차단
2. `sequence`·마감시각·중복 `submission_id` 검증
3. `private.question_options`에서 정답 조회
4. 판정(TS 엔진) 결과로 `at_bats` INSERT
5. `play_sessions`의 아웃·주자·득점·연속 UPDATE
6. 종료 시 `user_batting_stats`·`user_zone_cells` 증분, `xp_transactions` INSERT

선택지는 둘이었다.

- **(A) plpgsql 함수(RPC)로 전부 처리** — 원자성은 얻지만 판정 규칙이 SQL과 TS에 **이중으로 존재**한다. 승급 규칙이 바뀔 때 두 곳을 고쳐야 하고, 단위 테스트는 DB를 띄워야 한다.
- **(B) 서버에서 트랜잭션을 열고 TS 엔진을 단일 진실로 둔다** — 판정 규칙이 한 곳에만 있고 순수 함수라 테스트가 즉시 가능하다.

**(B)를 채택한다.** 판정은 `src/lib/engine/`의 순수 함수가 유일한 출처이고, `postgres.js`의 `sql.begin()` 안에서 읽기·판정·쓰기를 수행한다.

주의할 점:
- 서버리스 환경에서는 **Supavisor 트랜잭션 모드 풀러**를 쓰고 `prepare: false`로 준비된 구문을 끈다. 커넥션 수 상한과 현재 권장 설정은 **구현 시 공식 문서로 재확인**한다.
- 연결 문자열(`DATABASE_URL`)은 **서버 전용**이며 `NEXT_PUBLIC_` 접두사를 절대 붙이지 않는다.
- `supabase-js`의 `service_role` 클라이언트는 RLS를 우회하므로 **서버 모듈에서만 import**하고, 클라이언트 번들에 섞이지 않도록 `src/server/` 경계를 ESLint 규칙으로 강제한다.

### 3.2 정답 비노출 강제

- 정답은 `private.question_options.is_correct`에만 존재하고, **`anon`/`authenticated` 역할에는 권한을 주지 않는다.**
- 문항 조회는 `src/lib/db/queries/questions.ts`의 **단일 함수**만 통과하게 하고, 이 함수는 `is_correct`·`explanation`을 **타입 레벨에서 반환하지 않는다**(`PublicQuestion` 타입).
- 직렬화 후 페이로드에 금지 키가 없는지 검사하는 테스트를 둔다(§7.2 TC-SEC-01).

## 5. 구현 순서

각 단계는 §6의 완료 조건(DoD)을 만족한 뒤 다음으로 넘어간다. 단계 내에서도 **테스트를 먼저 쓴다**(엔진은 특히).

### 단계 1 — 프로젝트 골격 (0.5주)

1. Next.js + TypeScript + Tailwind 초기화, `strict: true`, 경로 별칭 `@/*`.
2. shadcn/ui 초기화 후 **08 §2 토큰을 `globals.css`의 CSS 변수로 구현**(다크 기본 + 라이트 파생).
3. ESLint·Prettier·Vitest·Playwright 설정. **`src/server/**`를 클라이언트 컴포넌트에서 import하면 lint 에러**가 되도록 규칙 추가.
4. `.env.example` 작성(아래 §8), `.env.local`은 `.gitignore` 확인.
5. CI 워크플로 골격(§9).

### 단계 2 — DB 스키마 (0.5주)

1. `supabase init` → 로컬 스택 기동.
2. `supabase migration new ...`로 `0001`~`0010`을 **07 문서 DDL 순서대로** 작성.
   - `user_batting_stats`의 PK는 07 §3.4 주석대로 **`id` PK + `(user_id, season_id)` UNIQUE + `season_id is null` 부분 유니크**로 구현한다(식 PK 불가).
3. RLS 활성화 + **SELECT 정책만 생성**(쓰기 정책 없음), `GRANT/REVOKE` 최소 권한, `private` 스키마 비노출.
4. `seed.sql`로 구단 10개·카테고리 5개 투입.
5. `supabase db reset` 반복 가능성 확인, advisors/security lint 검토.

### 단계 3 — 판정 엔진 (0.5주) ★ 가장 먼저 테스트

1. `tests/unit/engine/*.test.ts`에 **07 §10의 TC 1~16을 먼저 작성**(실패 상태 확인).
2. `resolveAtBat` / `advanceRunners` / `applyAtBat` / `boxScore` 구현.
3. 전 케이스 통과. 커버리지 100% 목표(순수 함수이므로 달성 가능).
4. 엔진 모듈에 **IO·DB·fetch import가 없음**을 lint 규칙으로 고정.

### 단계 4 — 게스트 세션 + 경기 시작 (0.5주)

1. `src/proxy.ts`(Next 16의 미들웨어)에서 게스트 쿠키 발급 — httpOnly·Secure·SameSite=Lax, HMAC 서명, **서버에는 sha256 해시만 저장**. DB 행은 첫 경기 시작 시점에 지연 생성한다.
2. `POST /play/sessions` — 체험 상한 검사(KST `day_key`), 문항 풀 선택(카테고리·난이도 분포), 1번 타석 반환.
3. `GET /play/sessions/[id]` — 스코어보드·현재 타석·남은 시간 복원.
4. 정답·해설이 응답에 포함되지 않음을 통합 테스트로 확정.

### 단계 5 — 타석 제출 (1주) ★ 핵심

1. `POST /play/sessions/[id]/at-bats` — `sql.begin()` 트랜잭션 안에서 §3.1의 6단계를 수행.
2. 멱등성: 동일 `submission_id` → **기존 결과 그대로 반환**. 동일 `sequence` 재제출 → 동일 응답. 불일치 → `SEQUENCE_MISMATCH`.
3. 마감 초과 → `ANSWER_DEADLINE_EXCEEDED` + 해당 타석 `K` 확정.
4. 3아웃 → 이닝 전이, 목표 초과 → `finishSession`(통산 성적·XP 원자 반영).
5. `abandon`·`box-score` 엔드포인트.
6. 통합 테스트: 동시 2요청, 재시도, 마감 경합.

### 단계 6 — 경기 화면 (0.5주)

1. `PlayClient` 상태 머신(08 §4.2) 구현. 서버 응답이 최종, 화면 타이머는 표시용.
2. `VerdictOverlay` — 결과 배지 + **승급 사유 1줄** + 해설 토글 시 자동 전환 정지.
3. 실패 시 **자동 재시도 금지**, `GET state` 선조회.
4. 반응형 sm/md/lg + 가로모드 1×4 (08 §6).
5. 키보드 `1~4`·`ASDF`, 0.4초 입력 잠금, `aria-live` 규칙(08 §8.2).

### 단계 7 — 결과·게이트·승계 (0.5주)

1. `BoxScore` + `AtBatLog`(해설·출처 펼침).
2. `SignupGate` — **P1은 G1 단독**, 카드형·닫기 가능, 숫자 포함 문구.
3. `/auth` + `callback` — `returnTo`·게스트 쿠키 보존, 복귀 후 `POST /auth/claim-guest` 호출.
4. `claimGuest` — `select ... for update` + `claimed_by` 단일 설정으로 멱등 보장, `ClaimedBanner` 즉시 표시.
5. 온보딩 2단계 → 원래 결과 화면 복귀.

### 단계 8 — 기록·랭킹·공유·운영 (0.5주)

1. `/me/batting`(통산·시즌 토글), `/dashboard`, `/modes`, `/settings`.
2. `/rankings` 비율(최소 50타석)·볼륨 탭 + 기준 명시.
3. `opengraph-image.tsx` 공유 카드 — 닉네임·등급·핵심 3지표만, **문항·정답 제외**.
4. `/admin/questions` 최소본: 등록·출처·검증일·보기 4개·정답 1개 검증 후 승인 게시.
5. `npm run seed:questions <csv>`로 검수 문항 투입(검증 실패 시 전체 롤백).

> **문항 300개는 코드가 아니라 콘텐츠 과제다.** 임포터와 승인 플로우는 구현
> 대상이지만, 문항 자체는 데이터 사용권 확보 이후의 작업이다. 그 전까지는

### 단계 9 — 품질 게이트 (0.5주)

3. 성능 측정 후 **목표치와 실측치를 구분해 기록**.
4. 스테이징 배포 → 백업·롤백 리허설 → 승인 후 운영.

## 11. 문항 300개 공급 계획

- 카테고리 5개 × 60개, 난이도 초급 40% / 중급 40% / 고급 20%.
- 각 문항 필수 필드: 보기 정확히 4개·정답 1개, **출처 URL·원천명·검증일·승인자·버전**, `record_as_of`(기록 기준일), `era_year`.

- 게시는 `/admin`의 승인 플로우만 통과한다. CSV → `scripts/seed-questions.ts`는 **검증 실패 시 전체 롤백**.
- 신고·정정 플로우는 P1에 최소본으로 포함(신고 접수 + 운영자 비공개 전환).
